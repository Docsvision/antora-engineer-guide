= Отслеживание состояния системных служб

Для системных служб, включая {sett-serv}, {mc}, {appserv}, {wc}, {fs} и {ft} поддерживается проверка работоспособности при помощи HTTP-запросов, не требующих авторизации. GET-запрос возвращает ответ с информацией о состоянии службы. Каждая служба предоставляет три конечных точки (endpoint) с едиными путями, кодами и ответами в формате JSON:

* Проверка текущего состояния (_liveness_) -- проверяет доступность службы, при проверке не учитывается состояние БД и других служб.
* Проверка запуска (_startup_) -- возвращает результат запуска службы.
+
NOTE: Поскольку службы {fs} и {ft} выполняют фоновую работу по расписанию и не принимают прикладной трафик, для проверок _startup_ и _liveness_ может использоваться одна конечная точка `/health/live`.
+
* Проверка готовности (_readiness_) -- возвращает статус готовности службы.

NOTE: Необходимые параметры задаются администратором в оркестраторе, отдельные настройки опроса в службах не предусмотрены.

При успешной проверке служба возвращает `200` и `{"status":"Healthy"}`, при неуспешной -- `503` и `{"status":"Unhealthy"}`. Ответ не содержит чувствительных данных. Если служба не отвечает на HTTP-запросы, конечная точка недоступна.

[cols="26%,74%",options="header"]
|===

|Конечная точка	|Назначение

|`/health/live`
|Процесс отвечает по HTTP без проверки БД и других служб. Если процесс остановлен, конечная точка недоступна. При неуспехе _liveness_ оркестратор перезапускает экземпляр службы.

|`/health/startup`
|Служба завершила необходимую инициализацию. До успешного ответа _startup_ проверки _liveness_ и _readiness_ не выполняются.

|`/health/ready`
|Служба готова к штатной работе. При неуспехе _readiness_ экземпляр исключается из балансировки, но процесс не останавливается.

|===

== Условия и зависимости статуса системных служб

При запуске службы {dv} ожидают недоступные зависимости, продолжая инициализацию после их готовности без ручного перезапуска. При недоступности зависимости процесс службы не завершается по причине неудачной попытки подключения и повторяет текущее подключение к ней, пока не исчерпан лимит попыток или служба не остановлена операционной системой. Успешное подключение означает готовность зависимости, проверка работоспособности не выполняется.

Для зависимости из таблицы ниже выполняется серия попыток подключения, заданная настройкой `DependencyMaxAttempts`. Значение по умолчанию -- `5`. Настройка задаёт общее число попыток, включая первую, выполняемую сразу.

После каждой неудачной попытки рассчитывается время до начала следующей попытки:

[cols="50%,50%",options="header"]
|===
|Номер неудачной попытки |Базовое значение

|1 |2 секунды
|2 |4 секунды
|3 |8 секунд
|4 |16 секунд
|5 и последующие |30 секунд
|===

Количество неудачных попыток запуска можно изменить индивидуально для системных служб, поддерживающих проверку, при помощи настройки в конфигурационном файле `appsettings.json`. Настройка `DependencyMaxAttempts` располагается в секции `DocsVision` на одном уровне с `ServiceId`. Значение также может быть переопределено переменной окружения `DV_DocsVision__DependencyMaxAttempts`. Допустимо только положительное целое значение, если указано некорректное значение, инициализация завершается ошибкой без повторных попыток.

Базовое значение -- это интервал, включающий время выполнения текущей попытки подключения и последующую паузу. Из базового значения вычитается фактическая длительность неудачной попытки. Полученная пауза случайно уменьшается на величину от `0%` до `25%`.

Например, для четвёртой неудачной попытки базовое значение составляет `16` секунд. Если попытка подключения выполнялась `5` секунд, исходная пауза составляет `11` секунд. После случайного уменьшения на `0–25%` фактическая пауза будет находиться в диапазоне от `8,25` до `11` секунд.

Если длительность попытки равна или превышает базовое значение, следующая попытка выполняется через минимальную паузу `100` мс. Поэтому после первой и второй попыток при длительности запроса до `5 секунд` может фиксироваться задержка `0,1` секунды, так как базовые значения `2` и `4` секунды уже исчерпаны самим запросом.

Базовое значение удваивается после каждой неудачной попытки, но не превышает `30` секунд. Случайное уменьшение паузы выбирается независимо для каждого экземпляра службы и призвано снизить вероятность одновременных повторных обращений нескольких экземпляров службы к зависимости.

После успешного подключения ожидание зависимости прекращается, служба завершает инициализацию.

.Состав ожидания:
[cols="50%,50%",options="header"]
|===
|Служба |Зависимость при запуске

|{sett-serv}
|СУБД {of-sett-serv}

|{appserv}
|{sett-serv}

|{mc}
|{sett-serv}

|{wc}
|{sett-serv}

|{wf}
|{sett-serv}

|Служба {ws}
|{sett-serv}

|{fs}
|{sett-serv}

|{sm}

|===

Настройка `DependencyMaxAttempts` ограничивает число попыток подключения и не изменяет системное время ожидания запуска службы. Если системное время ожидания истекает раньше, службу останавливает операционная система. Для длительного ожидания администратор настраивает системное время ожидания запуска.

Если в Windows или Linux настроен автоматический перезапуск службы, после её остановки операционная система может запустить службу снова. Циклы запуска и ожидания зависимостей могут повторяться согласно настройкам ОС.

CAUTION: Описанное ожидание применяется при запуске службы. Восстановление после потери зависимости уже работающей службой в этот механизм не входит.

Если зависимость недоступна или при попытке подключения возникла ошибка, выполняются повторные попытки. Если причина ошибки в некорректной конфигурации (отсутствует или неверно задан обязательный адрес, строка подключения либо учётные данные), служба немедленно завершает инициализацию с ошибкой.

.В журнал записываются:
[cols="50%,50%",options="header"]
|===
|Событие |Уровень

|Неудачная попытка, если попытки ещё остались: номер попытки, недоступная зависимость и рассчитанная пауза до следующей попытки
|Предупреждение

|Зависимость доступна, инициализация завершена
|Информация

|Исчерпаны попытки или отсутствует обязательная конфигурация
|Ошибка, для исчерпания попыток -- зависимость, заданный лимит и причина последней неудачи

|===

Недоступность {sett-serv} не считается отсутствием настройки. Отсутствие настройки фиксируется только после успешного ответа {of-sett-serv}, в котором нет требуемого значения.

.Условия "startup" и "readiness":
[cols="20%,40%,40%",options="header"]
|===
|Служба |"Startup: Unhealthy", если |"Readiness: Unhealthy", если

|{sett-serv}
|БД {of-sett-serv} недоступна.
|БД {of-sett-serv} недоступна.

|{mc}
|Служба не отвечает на HTTP-запросы. В таком случае контрольная точка `/health/startup` недоступна.
|Служба не отвечает на HTTP-запросы. В таком случае контрольная точка `/health/ready` недоступна.

|{appserv}
|{sett-serv} недоступен. Отсутствие БД по умолчанию не блокирует _startup_.
|Проверяемая БД недоступна.

|{wc}
|{sett-serv} недоступен. Выбор {of-appserv} и наличие административной сессии не блокируют _startup_.
|Не выбран {appserv} или недоступна административная сессия для проверяемой БД.

|===

.Особенности работы конечных точек:
* _Startup_ и _readiness_ {of-mc} не проверяют доступность {of-sett-serv} и получение из него конфигурации.
* _Readiness_ {of-appserv} не препятствует служебным запросам {of-mc}, в том числе подключению базы по умолчанию.
* Настройки {of-appserv} и {wc}а сохраняются в Сервисе настроек через {mc} и применяются после перезапуска сервиса. До перезапуска _readiness_ определяется по применённой конфигурации.
* GET-запрос к конечной точке `/health/ready` для {wc}а проверяет административную сессию для БД, используемой {wc}ом в применённой конфигурации.
+
При передаче query-параметра `database` проверяется административная сессия только для БД с указанным псевдонимом (`alias`), БД из применённой конфигурации {wc}а при этом не проверяется.
+
* GET-запрос к конечной точке `/health/ready` для {of-appserv} проверяет доступность БД по умолчанию.
+
При передаче query-параметра `database` проверяется только доступность БД с указанным псевдонимом (`alias`). БД по умолчанию при этом не проверяется. Проверка доступности БД не создаёт отдельной настройки таймаута.

== Примеры запросов

{appserv} не выбран для {wc}а::
В применённой конфигурации {wc}а {appserv} не выбран. В {of-mc} выбран {appserv} и сохранены настройки, но {wc} ещё не перезапущен.
+

|===

|Направление запроса |Пример |Ожидаемый результат

|`GET \http://адрес-сервера-{wc}а:ПОРТ/health/startup`
|`200`

|Запрос к {wc}у, _readiness_
|`GET \http://адрес-сервера-{wc}а:ПОРТ/health/ready`
|`503`

|===

+

|===

|Запрос к {to-appserv}, _readiness_

|`503`

|Запрос к {wc}у, _startup_
|`GET \http://адрес-сервера-{wc}а:ПОРТ/health/startup`
